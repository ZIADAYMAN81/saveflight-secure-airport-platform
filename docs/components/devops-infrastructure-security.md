# DevOps / Infrastructure Security

## Design

Infrastructure's job here is to make sure the application-level security work (encryption, RBAC, audit logging) is actually delivered over a hardened transport, running in hardened containers, on a segmented network — and to make sure none of that is just a config file that looks right on paper. The guiding principle for this layer was **verify by running, not by reading**: every control described below was confirmed by actually starting the full Docker Compose stack and the live Railway deployment and observing the behavior, which is how several real bugs were found that a static review of the YAML would have missed entirely.

## Component / Specification

Two deployment topologies, described fully in `docs/ARCHITECTURE.md` and `docs/DEPLOYMENT.md`: a full 6-container Docker Compose stack (`postgres`, `postgres_exporter`, `backend`, `frontend`, `nginx`, `prometheus`, `grafana`) on an isolated bridge network, and a combined single-container Railway deployment (backend + built frontend in one process) adopted specifically because the available Railway account's free-tier quota couldn't fit the full multi-service topology. Nginx is the TLS-terminating edge for the Compose stack: it redirects all HTTP to HTTPS, applies OWASP security headers, and rate-limits the auth endpoints more strictly than general API traffic. Prometheus scrapes backend and Postgres metrics; Grafana visualizes them.

## Security Implementation

**TLS + headers**, applied redundantly at two layers on purpose: nginx sets `Strict-Transport-Security`, `X-Content-Type-Options`, `X-Frame-Options`, `Content-Security-Policy`, etc. on every response, and the backend's own `SecurityHeadersMiddleware` sets the identical set independently — so the guarantee holds in the Railway topology too, where nginx isn't in front of the app at all. **Two-layer rate limiting**: nginx's `limit_req`/`limit_conn` rejects excess traffic before it reaches the Python process; `slowapi` inside FastAPI enforces the same intent at the application layer, again so the Railway single-container deployment isn't left unprotected. **Container hardening**: the backend runs with `read_only: true` (only `/tmp`, a `tmpfs` mount, is writable) and `security_opt: [no-new-privileges:true]` on both app containers, plus explicit CPU/memory limits and capped log file sizes on every service. **Network segmentation**: all services share one custom bridge network; Postgres, its exporter, and Grafana's backing store have no host port mapping at all — reachable only from other containers on that private network, never from outside the Docker host. **Encrypted backups**: `pg_dump` output is immediately AES-256-CBC+PBKDF2-encrypted via `openssl enc`, with the unencrypted intermediate file deleted right after — minimizing the window a plaintext dump exists on disk at all.

Real bugs found by actually running this stack, not by reviewing the compose file: both the `backend` and `frontend` Dockerfiles' `HEALTHCHECK` directives used `http://localhost:...`, which resolves to the IPv6 loopback `::1` first under Alpine/musl — but nginx and the app only bind IPv4, so every healthcheck failed continuously despite the services actually serving traffic correctly the whole time. This was invisible from reading the Dockerfile; it only showed up as containers marked `unhealthy` in `docker ps` once actually run. Fixed by hardcoding `127.0.0.1`. Separately, the `prometheus` service had no `ports:` mapping in an earlier revision — internal scraping worked fine (masking the issue), but the dashboard was completely unreachable from a browser on the host; only caught by trying to actually open `localhost:9090`. And `seed_demo_data.py` crashed under the backend's `read_only: true` constraint when it tried to write a reference file outside `/tmp` — proof the read-only boundary was genuinely enforced, not just declared, since the failure was a real filesystem-level `OSError`, not a logic bug.

## Testing Approach and Results

Infrastructure controls are largely not unit-testable in the pytest/Jest sense — they were verified operationally: `docker compose up --build` was run to completion and each container's health status, port reachability, and log output were inspected directly; `curl -I` against both the local nginx edge and the live Railway URL confirmed the expected security headers were present in the actual HTTP response, not just configured in a file; `docker port airport_postgres` confirmed no host-side binding exists for the database; a real backup was taken, confirmed unreadable as SQL without the encryption password, and successfully restored into a fresh Postgres container end-to-end. Where the backend's own test suite does cover infrastructure-adjacent behavior (e.g., rate limiting), those tests are cited in `docs/TESTING_VALIDATION.md §3.2`.

## Setup & Deployment

Full instructions, including the exact bugs found and fixed during first real runs of each topology, are in `docs/DEPLOYMENT.md`. Summary: `docker compose up --build` for the full stack (after generating a local dev TLS cert and populating `.env`); `railway up` for the combined single-container deployment, with environment variables set once via the Railway dashboard/CLI and never committed to the repo.
