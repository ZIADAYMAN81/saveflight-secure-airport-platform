# Backend / Database Security

## Design

The backend owns everything that must never be trusted to a client: identity, cryptography, business-logic invariants, and the record of what happened. It's a FastAPI application organized as one router per domain (`auth`, `passenger`, `booking`, `payment`, `staff`, `admin`, `seat`, `flight_status`, `analytics`), each mounted under `/api/v1/...`, backed by PostgreSQL via SQLAlchemy ORM. The guiding design principle throughout was: **the server is the only party that can be trusted to enforce a rule, so every security-relevant decision — who you are, what you're allowed to touch, what something costs, whether a seat is free — is decided server-side, using data the server itself fetched, never a value the client sent.** Concretely, this shows up as: role is read from the freshly-queried `User` row (not just trusted from the JWT claim), payment amounts are computed from `Flight.base_price` (there is no `amount` field in the request schema at all), and seat availability is checked against a live DB query at the moment of booking, not a client-supplied "is this free" flag.

## Component / API Specification

Five database entities anchor the model: `User` (identity + auth state — hashed password, role, TOTP secret, lockout counters), `Passenger`/`Staff` (role-specific profile data, 1:1 with a `User`), `Flight`/`Seat`/`Booking` (the operational core), `PaymentRecord`, and `AuditLog`. The API surface is REST, versioned (`/api/v1`), and every mutating or sensitive-read endpoint declares its required role via a `Depends(require_role([...]))` dependency at the route level — this is visible directly in each router's decorator, not buried in business logic, so an unauthenticated reviewer can audit access control by reading route signatures alone. Key endpoints: `POST /auth/register` (passenger self-signup only — role is hardcoded server-side, never accepted from the client), `POST /auth/login` → `POST /auth/2fa-verify` (two-step for staff), `POST /booking/create`, `POST /payment/process`, `GET /admin/audit-logs/verify`.

## Security Implementation

Five mechanisms carry most of the security weight. **Argon2 password hashing** (`passlib.CryptContext`) with progressive lockout (5 failed attempts → 15-minute lock) defends the credential itself. **AES-256-GCM field-level encryption** (`security.py:encrypt_data`, using `cryptography.hazmat`'s `AESGCM` directly rather than the `Fernet` recipe, since Fernet's AES-128 doesn't meet an explicit AES-256 requirement) protects passenger PII at rest — passport numbers and addresses are opaque base64 blobs in the actual Postgres rows, verifiable by inspecting the table directly. **JWT + server-enforced RBAC** (`create_access_token`/`decode_access_token` with pinned `HS256`, `require_role()` re-checking the live DB role on every request) is the authorization backbone across all five roles. **A SHA-256 hash-chained audit log** (`audit.py`) makes tampering with historical security events detectable: each row's hash commits to the previous row's hash, so altering any one row breaks the chain for every row after it — this was specifically verified by writing a test that performs a raw SQL `UPDATE` against an audit row (bypassing the application entirely) and confirming `verify_chain_integrity()` correctly flips to `false`. **RSA-2048 digital signatures on boarding passes** (`security.py:sign_boarding_pass`/`verify_boarding_pass_signature`) add genuine asymmetric-key cryptography to the system, distinct from JWT's `HS256` — which is a symmetric HMAC and therefore not a true digital signature (no non-repudiation, since the same key that verifies could also sign). The private key never leaves the server; the public key is exposed at an unauthenticated `GET /api/v1/boarding-pass/public-key` endpoint specifically so verification never requires trusting whoever presents the pass. This closes a real gap the earlier opaque-token-only design had: a compromised database credential editing a booking's flight/seat directly (bypassing the app) would leave the token still matching, but the signature — computed over the values at issuance — no longer would, and redemption is correctly rejected.

A concrete example of design-under-pressure: the initial staff 2FA flow had a bootstrapping bug — a newly created staff account (via `/admin/create-staff`) had no TOTP secret yet, but login hard-required 2FA, and enrolling a TOTP secret required already being logged in. The fix was to always send an emailed OTP as an alternate 2FA factor regardless of TOTP enrollment status, and have `/2fa-verify` accept either a valid TOTP code or a valid (single-use, 5-minute-expiry) emailed OTP — closing the chicken-and-egg gap without weakening the 2FA requirement itself.

A second example, this time from supply-chain hygiene rather than application logic: running `pip-audit` against `requirements.txt` for real (not just as a checklist item) surfaced 37 known CVEs across 7 packages, including `cryptography` and `python-jose` — both directly load-bearing for this system's encryption and JWT handling. These were fixed by upgrading pinned versions, each change verified against the full test suite before being kept. Two of the remaining findings were deliberately *not* force-fixed after investigation: `pyasn1`'s patched version directly conflicts with `python-jose`'s own declared dependency constraint, and `ecdsa`'s vulnerability sits in a code path (`ES256`) this system never uses (`HS256` only) — both documented with reasoning in `docs/SECURITY.md` rather than silently ignored.

## Testing Approach and Results

85 backend tests (pytest + FastAPI's `TestClient` against a real, ephemeral SQLite DB per test session — not mocked) organized by concern: `test_auth.py` (hashing, lockout, 2FA, rate limiting), `test_rbac.py` (every role boundary tested both ways — can/cannot access), `test_payment_and_audit.py` (price-tampering resistance, audit chain integrity), `test_passenger_flow.py`/`test_staff_flow.py` (end-to-end booking→check-in→boarding-pass), `test_seats_and_status.py` (seat collision/restriction, class pricing), `test_analytics.py` (verifies dashboard figures are computed from real rows, not fabricated), and `test_security_properties.py` (encryption round-trip with tamper detection, JWT expiry enforcement, SQL-injection-attempt resistance, RSA signature validity and tamper detection). Every test hits real application code paths — no security mechanism is mocked out, since a mocked encryption call or a mocked RBAC check would prove nothing about whether the real implementation works. Backend code coverage: 90% (`pytest --cov=src`, scoped via `.coveragerc` to exclude one-off bootstrap/seed scripts).

## Setup & Deployment

```bash
cd backend && python -m venv venv && venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env    # set DATA_ENCRYPTION_KEY, JWT_SECRET for anything beyond local dev
python -m src.init_db
uvicorn src.main:app --reload --host 0.0.0.0 --port 8000
```
Full deployment (Docker Compose and Railway) is documented in `docs/DEPLOYMENT.md`.
